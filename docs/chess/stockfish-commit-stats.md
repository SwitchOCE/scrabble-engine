## Definitions

- **result** (from SPRT lines in the message): *gain* = passed an SPRT with gainer bounds (midpoint of the Elo bounds > 0) at the longest single-thread TC tried; *mixed* = passed a gainer SPRT at a shorter TC but failed at the longest; *nonreg* = passed only non-regression bounds (midpoint <= 0, e.g. `<-1.75,0.25>`); *tested-not-passed* = results present but none passed (fixed-game runs, failed or stopped tests quoted for context); *untested* = no results in the message.
- **kind** (from subject, body and files; first rule wins): release ("Stockfish 15", "Restore development version") > build-ci-docs (only non-source files) > net-update (subject names a net `nn-xxxx`, "update ... net", or an SFNNv architecture bump; from 2020-08 only) > tuning (spsa/tune) > speedup > non-functional ("No functional change" line) > simplification (simplify/remove/cleanup/refactor subject, or result nonreg) > bugfix > other-functional.
- **areas**: from files touched (one commit can have several). `evaluate` is src/evaluate.*: classical eval before 2020-08, NNUE glue after 2023-07, both in between. Net-update commits also get `nnue`.
- **techniques**: keyword tags on the subject and the text before the first test result. NNUE tags only from 2020-08-06. Heuristic; see Accuracy below.
- **LTC Elo**: logistic Elo recomputed from W/L/D of the first passed gainer LTC test (single-thread only, default configuration: tests labelled MultiPV, Skill, Chess960/FRC, contempt, ponder or MAX_PLY, and commits whose subject names MultiPV, Skill, Chess960/FRC or ponder, are left out). Not the SPRT bound and not fishtest's normalized Elo.

## How this was made

- Source: `git log --no-merges` of official-stockfish/Stockfish at
  `5d03b6e578a5eedc822e4563bdbb89e762fc2a59` (pin in `reference/PINS.tsv`, 2026-11-15),
  7297 non-merge commits from 2008-09 to 2026-11. Dates are committer dates (when the
  patch landed on master). PR numbers are filtered against
  `reference/history/stockfish/prs-index.tsv`.
- Command: `python3 -I scripts/parse-stockfish-commits.py` (standard library only, about
  3 s on a 6-core Linux laptop). Rerunning regenerates everything above the marker.
- The reference clone is blobless (`git clone --filter=blob:none`, see
  `scripts/fetch-references.sh:25`). The first draft of the script used `--numstat`,
  which makes git fetch every blob over the network; it hung with no output. The script
  now reads files touched with `--name-status --no-renames`, which needs only trees, so
  **lines added/removed are not reported**.
- Elo-model brackets follow fishtest's own formatter: `[]` BayesElo, `{}` logistic,
  `<>` normalized (official-stockfish/fishtest `d26351d9`,
  `server/fishtest/util.py:254-258`, `format_bounds`).

## Accuracy and limits

### Spot-check

62 commits checked by hand against `git -C reference/stockfish show -s <sha>`, in three
rounds. Each commit counts as "fully right" only if every field is right: tests found,
TC, LLR, bounds and Elo model, gain/nonreg, W/L/D and Elo, URL, PR, result, kind, areas,
technique tags. Per-commit verdicts and what was fixed:
[`data/stockfish-spotcheck.tsv`](data/stockfish-spotcheck.tsv).

| round | sample | when | fully right |
|---|---|---|---|
| 1 | 14 random (one per year 2013-2026) + 18 picked for odd formats | after the first rewrite | 19 / 32 |
| 2 | 20 hold-out (new seed: one per year + 6 random tested commits) | after round-1 fixes | 13 / 20 |
| 3 | 10 hold-out (new seed: 7 tested, 3 untested) | after round-2 fixes | 7 / 10 |

Every error found was fixed with a general rule (and its reach measured) except one
(f21610e5, below). Fixes were made after looking at the errors, so rounds 1-3 are not
estimates of the final accuracy. **The best estimate for unseen commits is the hold-out
rate before fixing: 65-70% fully right.** Most errors were in the heuristic fields
(kind, technique tags). In all 62 commits the LLR values, bounds and W/L/D counts were
read correctly. The errors in the test fields were: TC (2), threads (2), URL (2),
gain/nonreg (1), reverse tests (2), result when STC passed and LTC failed (1), PR (1).

### Automated checks over the whole history

- **Elo formula.** 165 tests print their own Elo (`ELO: x +- y` or `Elo: x ± y`, from
  fixed-games runs). The recomputed Elo equals the printed value to within 0.01 in all
  165, including the pentanomial error bar (af110e02: printed -2.35 ± 1.1, recomputed
  -2.35 ± 1.09).
- **W/L/D sums.** `Total` differs from W+L+D in 1 of 4928 tests.
- **PR numbers.** 2849 of 3138 "closes/resolves" PR numbers have a PR title similar to
  the commit subject (difflib ratio >= 0.5), and no PR is dated after its commit. The
  low-similarity ones sampled were retitled PRs or cleanup commits that close several
  PRs (the script keeps the last). The fallback (exactly one Stockfish PR link, no
  "closes" line; `pr_source=mention`, 59 commits) matches the title in 50 of 59 (85%).
- **SPRT sanity.** No passed gainer LTC test with logistic or normalized bounds has a
  recomputed Elo below its `elo0`.

### Field coverage

See the "Field coverage" table above. In short: 97% of SPRT tests have a time control
(most from a named label like "STC"/"LTC"; the rest from "short/long" wording, a
numeric TC like `60+0.6`, or STC-then-LTC order); 99% have Elo bounds; 100% have W/L/D;
81% have a fishtest URL; 82% of gain commits have an LTC Elo. No commit before 2013
quotes a test result, so "untested" there means "no data", not "not tested".

### Known misclassifications and limits

- **Kind and technique tags are keyword rules.** They record what a message mentions,
  not what the patch changed (9cc15b30 is tagged `iir` because it compares itself with
  IIR). Tags overlap; a commit often gets 3-5. In the 62-commit sample, 9 commits (15%)
  had at least one wrong technique tag before fixes; recall was not measured. Technique
  tags are good enough to rank broad techniques by count and Elo, not to cite a single
  commit.
- **Reliability for ranking.** The fields the ranking tables use (result gain/nonreg,
  LTC Elo, areas from files) had no error in the hold-out rounds after round-1 fixes
  except result in 3 of 30 commits (two reverse tests, one STC-pass/LTC-fail), all since
  fixed. Areas are exact as file facts; their meaning is coarse (see next point).
- **Areas come from file paths.** `evaluate` mixes classical eval (before 2020-08), the
  hybrid era (2020-08 to 2023-07) and NNUE glue code (after af110e02 "Remove classical
  evaluation", 2023-07-11). Net updates change only `src/evaluate.h`; they are tagged
  `nnue` through the net-update rule.
- **Odd layouts.** f21610e5 has one LTC block with two LLR lines and no colons; the
  script reads one passed non-regression test with no TC there. Results quoted for
  context (other patches, earlier versions) are counted as this commit's tests.
- **"mixed" (11 commits)**: passed a gainer SPRT at a shorter TC, failed at the longest.
  Several were merged anyway (speedups, a mate-finding fix), so "mixed" is not "rejected".
- **Reverse tests** ("master vs patch") are detected only when the label says so (4 tests).
- **Two unlabelled SPRTs** are read as STC then LTC (58 tests, `tc_source=order`). This
  matches 2013-2014 practice (bb83a417 labels `[-1.5,4.5]` as 15+0.05 and `[0,6]` as
  60+0.05), but is still a guess.
- **Merges excluded** (53 merge commits). PR numbers are missing for commits pushed
  directly (22% of commits from 2014-06 on).

## What the Elo numbers do and don't mean

- They are **self-play Elo at one time control** against the master of the day, from
  fishtest's opening books. They are not Elo against other engines or humans, and not
  cumulative strength. Sum them and you get a number with no meaning: patches interact,
  gains shrink at longer TC, and several are measured against the same base.
- **Selection bias.** An SPRT stops when the LLR crosses a bound. Patches that pass are
  partly the lucky ones, so the Elo of passed tests overstates the true gain, most for
  short tests near the bound (winner's curse). Failed tests are mostly not in commit
  messages at all, so the data shows what was kept, not what was tried. (Inference;
  Stockfish's own regression tests between releases are the right source for
  cumulative gain.)
- **Not comparable across eras.** LTC was 60+0.05 in 2013 (f7c013ed, bb83a417) and
  60+0.6 later (84f3e867). Bounds in messages are BayesElo until 2019, logistic from
  2020-01-07 to 2021-04-28, normalized from 2021-04-25 (dates of first/last use in
  `data/stockfish-tests.tsv`). Draw rates and opening books changed over time (UNVERIFIED: the
  switch to unbalanced UHO books around 2021 widened Elo differences per patch).
  Medians per year are a trend in "size of a typical accepted patch at LTC", not in
  strength.
- **Non-regression tests carry no gain claim.** Their Elo is close to 0 by design and is
  not used in the Elo columns.

## Inference

These are readings of the tables above, not measured facts.

- Since 2014, about half of all tested commits passed only non-regression bounds
  (1158 nonreg vs 1254 gain overall; more nonreg than gain in 2016-2019 and 2023-2025).
  Stockfish spends about as much testing on removing or simplifying code as on adding
  strength. That is a process idea a Scrabble engine can copy directly: a cheap
  non-regression SPRT for every simplification.
- The typical accepted patch shrank: median LTC Elo of gain commits fell from 3.4
  (2013-2015) to 2.3 (2016-2019), 1.7 (2020-2022) and 1.5 (2023-2026). Late gains come
  from many patches of about 1.5 Elo each, which only a large testing setup can detect.
- New networks (100 net-update gain commits with LTC Elo, median 2.0) and parameter
  tuning (89, median 2.1) are each as large a source of accepted gains as any single
  search technique. By tag, the largest search sources are reductions/LMR, history
  heuristics (incl. correction history from 2023-12) and extensions.

## Open questions

- **Line counts.** Diff size per commit needs blobs. Either fetch them once into the
  clone (`git -C reference/stockfish fetch --refetch` without a filter; size unknown,
  network needed) or take additions/deletions from `reference/history/stockfish/prs.json`
  for the 78% of commits with a PR. Not done.
- **Exact test settings.** 81% of tests link a fishtest run. The fishtest API would give
  the exact TC, book, threads and normalized Elo. Check the API's rate limits and terms
  before fetching ~4000 runs.
- **Tag quality.** Precision of the technique tags is a rough sample figure and recall
  is unknown. A hand-labelled set of ~100 gain commits would measure both, and would be
  the base for mapping chess techniques to Scrabble ones (research track R3).
- **Rejected ideas.** Commit messages show only accepted patches. PRs that no commit
  "closes" (most Stockfish PRs show CLOSED even when accepted, so state alone does not
  tell) and fishtest's failed runs hold the ideas that did not work. Which are worth
  mining?
- **Cumulative strength.** Should we join this table with Stockfish's release-to-release
  regression results to see which periods (and so which kinds of change) moved
  strength most?
